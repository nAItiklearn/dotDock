# Incident 2026-11-21: the dock swallowed clicks on the whole desktop

## What the owner saw
During the dock-host live run the dock was on the desktop, did not respond the way it should, and no app on the
desktop could be opened. The owner closed the session; the desktop was left clean (no `dotdock.exe`, taskbar
visible, auto-hide on).

## Root cause
The dock window is a transparent sheet the size of the monitor. It is click-through (`WS_EX_TRANSPARENT`) except
while the cursor is inside the rectangles the UI reports with `dock_set_regions`; the host's pointer poller
(`dotdock-dock`, `host/pointer.rs`) turns the click-through bit off while the cursor is inside one of them.

`computeRegions` in the dock UI (`apps/desktop/src/dock/regions.ts`) returned **the whole window** as the region
whenever anything "modal" was open: a context menu, a stack, a tile popover, the widget gallery, the settings
popover or the App Library. While any of those was open, the cursor was "inside" everywhere, so the sheet took
every click on the monitor. Only a click on the dock's own scrim closed the panel; a click anywhere else on the
desktop landed on the invisible sheet, and the apps beneath never received it. Opening one menu was enough to
make the whole desktop look dead.

## Fix
- **Regions are only what is drawn** (dock UI, 8d96d13, merged into this branch): the bar plus `HIT_MARGIN`, grown by
  the magnification headroom only while the pointer is on it; a 4 px hot strip while auto-hidden; each open popover,
  menu, gallery or preview as drawn, plus `HIT_MARGIN`. The full window only while the App Library is open, because
  the library is drawn full-screen. Open panels close when the dock window loses focus, so a click on another app
  both reaches that app and closes the panel. Unit tests: `regions.test.ts`.
- **Kill switch** (host): Ctrl+Alt+Shift+D quits dotDock from any state; the exit handler stops the host and restores
  the taskbar through the D0 guard. The tray menu item is now "Quit and restore Windows". The D0 sentinel still
  restores the taskbar if the process hangs or dies.
- **Real-desktop test** `tools/dock-tests/clickthrough.ps1`: with the dock running it clicks a Notepad window next to
  the dock, the desktop beside the bar, opens a dock menu and clicks Notepad again (the click must reach Notepad and
  close the menu), checks that the window under a point far from the dock is never the dock while a menu is open,
  launches Chrome from the dock, then presses the kill switch and checks that dotDock is gone, the taskbar is
  visible and auto-hide is on. Results are appended to `LIVE_LOG.md`.

## Why the window stays monitor-sized
The owner asked for a window exactly the bar's shape. The hit area is that shape: outside the regions above the
window is click-through, which is the property that matters for input. The window itself stays the size of the
monitor because stacks, menus, previews and the App Library are drawn in it; resizing the WebView2 window for
every popover would relayout and repaint it on each open, which costs the "open in the first frame" guarantee
(DOCK_SPEC 4). Decision D-006 already chose cursor polling over `SetWindowRgn` for the same reason.

## Rule added for live runs
Before the owner sees a run, `clickthrough.ps1` must pass on the real desktop. On any failure the script quits
dotDock and restores the taskbar itself. Every run ends with dotDock quit, the taskbar visible and auto-hide on,
checked with `tools/check-desktop.ps1`.
